        一句话核心痛点

        这个系统要解决的是：大模型在做因果推理时会产生"拓扑幻觉"（凭空捏造环路、混淆因子、伪独立关系），而传统 LLM
        推理管线对此毫无免疫力。EdgeThemis 用 Rust 编译期保证的图论算法作为"测谎仪"，在 LLM
        每一次吐出因果图后，强制执行数学级验证（d-分离 + 环检测），再把破绽反向注入 prompt 让 LLM
        自我纠错——本质上是把"形式化验证"嵌入到了 LLM 的推理循环中。

        3.1 时序图：一次完整推演的子弹轨迹

        sequenceDiagram
        participant User as 用户 (app.py)
        participant LG as LangGraph 状态机
        participant Gen as Generator 节点
        participant LLM as llama-server (C++ 进程:8080)
        participant Val as Validator 节点
        participant Rust as Rust 引擎 (FFI)
        participant Ref as Reflector 节点

        User->>LG: stream(initial_state)
        LG->>Gen: generate_graph_node(state)
        Gen->>LLM: HTTP POST /v1/chat/completions<br/>(json_schema 约束 + ExtractedGraph)
        LLM-->>Gen: JSON (reasoning_process + edges[])
        Gen-->>LG: {extracted_graph, current_phase}

        LG->>Val: validate_graph_node(state)
        Val->>Rust: FmeaScore(s,o,d).calculate_rpn() [逐边]
        Val->>Rust: AgentContext().__enter__() → CausalParadigmEngine
        Val->>Rust: inject_edges(py_edges) [字符串驻留 + 邻接表构建]
        Val->>Rust: check_graph_health() [Kahn 算法]

        alt 检测到环路
                Rust-->>Val: false (有环)
                Val-->>LG: {is_safe:false, d_separation_claims:[]}
                LG->>Gen: 路由回 generate_graph (携带拦截报告)
        else 无环路
                Val->>Rust: extract_testable_claims() [O(N³) 贝叶斯球]
                alt 发现 d-分离破绽
                Rust-->>Val: Vec<String> 物理断言
                Val-->>LG: {is_safe:false, d_separation_claims:[...]}
                LG->>Ref: reflector_node(state)
                Ref->>LLM: HTTP POST (ReflectorVerdict 约束)
                alt REJECT
                        LLM-->>Ref: {verdict:"REJECT", reason:"..."}
                        Ref-->>LG: {is_safe:false}
                        LG->>Gen: 路由回 generate_graph
                else PASS
                        LLM-->>Ref: {verdict:"PASS", reason:"..."}
                        Ref-->>LG: {is_safe:true}
                        LG-->>User: 结案
                end
                else 无破绽
                Rust-->>Val: vec![] (空)
                Val-->>LG: {is_safe:true, d_separation_claims:[]}
                Val->>Rust: AgentContext().__exit__() → Drop 死神 + gc.collect()
                LG-->>User: 结案
                end
        end

        3.4 质疑与逻辑断层清单

        #: 1
        位置: context_guard.py:17
        问题: Rust 引擎在 Validator 每次调用时都 new() 重新实例化，这意味着每次验证都重建字符串驻留池和空图——整个 inject_edges

        → check_graph_health → extract_testable_claims 都在同一轮 with AgentContext()
        里完成，所以没问题。但如果未来需要在多次调用间保持图状态，当前设计无法支持。
        严重性: 低（当前架构下无影响）
        ────────────────────────────────────────
        #: 2
        位置: nodes.py:81
        问题: max_tokens=512 对因果图提取是否足够？ 一个复杂场景的 reasoning_process + 多条 edges 很容易超 512 token，导致
        JSON
        截断 → ValidationError → 循环消耗熔断次数。
        严重性: 高
        ────────────────────────────────────────
        #: 3
        位置: algorithms.rs:63-149
        问题: d-分离算法的时间复杂度是 O(V²)（外层 BFS 每节点一个状态×方向），但 extract_testable_claims 是 O(V³)（遍历所有
        (X,Y) 对 × 遍历所有 Z）。当节点数超过 50 时，Rust 侧会锁住 Mutex 很久，Python 侧会阻塞等待。
        严重性: 高（OOM / 阻塞风险）
        ────────────────────────────────────────
        #: 4
        位置: lib.rs:103
        问题: inject_edges 拿锁后遍历所有边做 insert_full，如果边数很多，Mutex 锁持有时间会很长，阻塞其他可能的并发读取。
        当前单线程场景无影响，但不符合"线程安全"的承诺。
        严重性: 中
        ────────────────────────────────────────
        #: 5
        位置: nodes.py:6
        问题: OpenAI client 在模块顶层实例化（client = OpenAI(...)），这意味着 import 时就会尝试连接。如果 llama-server
        没启动，import 就会卡住或报错，违反了延迟初始化原则。
        严重性: 高
        ────────────────────────────────────────
        #: 6
        位置: app.py:108-149
        问题: if __name__ == "__main__" 块中，final_extracted_graph 只记录最后一次出现的 extracted_graph，但如果 Generator
        被重试多次，每次都生成新图，只有最后一次会被保存。中间的 RPN 高危警报虽然打印了，但没有持久化到状态中。
        严重性: 中
        ────────────────────────────────────────
        #: 7
        位置: algorithms.rs:121-145
        问题: 贝叶斯球实现中，!is_down && !observed.contains(&curr) 这个条件在 line 121 和 line 136
        重复出现，两个分支都执行。这不是 bug（chain 和 confounder 的 up→down 和 up→up
        确实共享条件），但代码可读性极差，容易在修改时引入 bug。
        严重性: 低（可读性）
        ────────────────────────────────────────
        #: 8
        位置: lib.rs:36-42
        问题: LlamaMemoryReaper::drop() 里只设置了 is_active = false，注释中提到未来要调用
        llama_free，但当前是空操作。实际的显存释放完全依赖 llama-server 进程的退出，而不是 Rust 的 Drop。
        严重性: 低（当前架构下 llama-server 是独立进程，不是内嵌的）
        ────────────────────────────────────────
        #: 9
        位置: fmea_evaluator.rs:20
        问题: RPN 公式 100S + 10O + D 硬编码了权重，没有任何配置机制。这意味着 S=10,O=1,D=0 (RPN=1010) 和 S=5,O=5,D=5
        (RPN=555)
        的风险判定完全不同，但后者可能实际风险更高。
        严重性: 中（领域争议）

        3.5 架构核心洞察

        这个系统的真正巧妙之处在于三重异构边界的缝合：

        1. C++ ↔ Python：通过 HTTP（llama-server），将显存管理完全外包给独立进程，Python 侧零显存占用。
        2. Python ↔ Rust：通过 PyO3 FFI，将图论算法的数学正确性用 Rust 编译期保证，Python 无法篡改。
        3. LLM ↔ 形式化验证：通过 LangGraph 条件路由，将 LLM 的输出强制送入 Rust 验证，不过关就反向注入错误报告让 LLM
        自我纠错——形成闭环。

        但也正因为这三重边界，系统的可观测性极差：如果中间任何一环静默失败（比如 llama-server 返回了格式正确但语义空洞的
        JSON、或者 Rust 的 d-分离算法因为节点数过多而超时但没有超时机制），整个管线会默默重试直到熔断，而用户只能看到"连续发癫
        3 次"的日志，无法诊断根因。
